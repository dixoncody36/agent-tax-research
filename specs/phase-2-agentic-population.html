Decree: Phase 2 — Harness-Ready Agentic Population & Monitoring

Metadata

Purpose

Agent-first, human-last. Pulling tax rates, rules, licenses, and compliance obligations from primary sources — and keeping them current forever — is no longer a human function. In this system, agents discover, collect, structure, verify, and monitor; they write everything into the Phase 1 PostgreSQL database; downstream custom functions and services (sales/use-tax lookups, calculators, research tools) consume the published data. Humans do exactly one thing in the loop: final approval of agent-verified proposals, because humans are the slowest step and belong at the end of it.

Phase 2 builds that agent workforce as a harness-ready, clone-and-go system: clone the repo, describe your context (the jurisdictions, industries, and taxes you care about), point your agent harness at it — Muse first for the Meta hackathon, portable to Muse, Codex, Grok, OpenCode, Herdr-orchestrated lanes, or a headless Azure AI Foundry runner — and the cascade populates and monitors your slice of the world. The author's own deployment runs the full-globe context continuously as part of a consulting practice; a single-city business runs the identical code with a Dallas-only context.

Audit scope (027): audit-scoped — yes. Regimes: tax examination (federal/state; ASC 740 adjacency), internal audit / client review. Historical rates exist explicitly so past periods can be re-performed. Every published figure must trace to its extraction run, source snapshot, verifier, and human approver (see Data Model register and per-phase audit: validations).

Problem

Phase 1 proved the container: eight tables, Texas seeded, combined-rate lookup working. But the data was gathered by hand for 3 of 27 Texas levies — the other 24 are stubs, Texas alone has thousands of sub-jurisdictions, and the planet has roughly 200 countries whose tax authorities publish change continuously. No human team keeps that current, and vendor data (Avalara, Vertex, TaxJar class) is deliberately off-limits: this platform's value is research from the source, so every fact must come from public-facing government primaries. The gap between "a schema that can hold the world" and "the world, in it, current, with evidence" is an agent system: scoped by operator context, fenced to eligible sources, self-verifying, observable at every step, and runnable from whatever harness the operator already uses.

Solution

Three layers, each independently replaceable. (1) A harness-neutral core: the PostgreSQL database holds all state (work queue, runs, proposals, coverage, exceptions, snapshots), and a tax CLI with JSON assignments and result envelopes is the only interface agents use — no agent writes SQL, no state lives in a chat transcript. (2) Harness adapters: AGENTS.md carries the universal instructions; Muse gets the first-class adapter (Wonder conducting workflows/subagents, a kickoff that creates a session goal from the scope and reports progress from database state); Claude Code, Codex, Grok, OpenCode, and Herdr lanes need only "read AGENTS.md, call the CLI"; a headless runner calls Azure AI Foundry APIs directly with the same envelopes. Models are logical tiers in config/models.yaml — conductor (Wonder), worker (Glimmer-class), verifier (strong tier), embedder — mapped to harness-native models by default and Foundry deployments by environment override. (3) The contextualization layer (below) decides what any of this is allowed to touch.

Contextualization: the operator's fence, compiled before agents run

Most operators do not need the planet. A business operating only in Dallas, or Texas, or Brazil should pay — in tokens, time, and review burden — only for its footprint. Each deployment carries a tax-context.yaml: operating footprint (jurisdictions), industries, tax categories, activities/nexus triggers, materiality thresholds, monitor cadences, and history depth. The context compiler turns it into an explicit, reviewable scope: the jurisdiction set (ancestors always included — Dallas cannot be answered without Texas and US Federal for stacking and conformity), filtered question packs, the source subset, and per-jurisdiction cadences. The CLI enforces the compiled scope as a hard fence: out-of-context assignments cannot be created or claimed, and agents never widen their own scope. The repo ships a full-globe profile (the author's always-on consulting scan) plus Texas-only, Dallas-only, and Brazil-only worked examples — one codebase, any footprint.

# tax-context.example.yaml (abridged)
profile: dallas-only
footprint: [us-tx-dallas]          # ancestors auto-included: us-tx, us
industries: [retail]
categories: [sales_tax, franchise_margin, occupancy, property]
history: earliest_published
monitor: { state: weekly, local: monthly }

Jurisdiction context hooks: local knowledge, injected pre- and post-run

Standard question packs cannot know what a practitioner in the jurisdiction knows — that one authority's guidance lags its statute, that home-rule cities behave differently, that a term means something narrower locally. So every jurisdiction can carry a context pack: versioned local guidance and memory, authored by the humans who know that place, stored as data and mirrored to jurisdiction-context/<slug>.yaml for harness portability. Pre-run, the CLI injects the resolved packs (city inherits state and country; most specific wins) into every assignment envelope, so workers evaluate resources the local way from the first fetch. Post-run, hooks at the proposal, verified, and published transitions run jurisdiction-specific checks, route notifications to the local expert, and let agents propose memory updates from what they learned — approved by a human before they stick, append-only like everything else. The precedence rule is absolute: injected context steers interpretation and search; it is never evidence, cannot relax source eligibility or the context fence, and any conflict with a primary source becomes a typed exception rather than a quiet override.

Four specified roles — objective slots, operator-chosen models

RoleOwnsNever does

Each role is a slot in config/models.yaml — the operator assigns any model to any role (Wonder orchestrating, Glimmer fetching, stronger models deciding/reviewing, or any other mix). Roles are enforced by the CLI: an assignment names its role, run identities are role-stamped, and gates require fetch, decision, reviewer, and human approver to be distinct identities. Check-first, then research: validated determinations live in the research ledger with their snapshot hashes and handoff notes; future runs must read them first and reuse anything still valid. Prior work reopens only on a typed invalidation — source changed, human objection, cadence expiry, context or pack change — targeted, never a blanket redo. The final stage of any completed jurisdiction is a generated tax guide written from published data alone: rates, rules, licenses, compliance, history, confirmed absences, and honest unknowns, version-stamped and regenerated on material change.

Question standard. Coverage is interrogation, not collection. Category question packs (rate, base, exemptions, thresholds, permits, filing, penalties, history) combine with the peer-profile catalog — the union of tax types found in already-profiled jurisdictions — so each new jurisdiction is asked about everything its peers have, under any name. Answers are found (eligible citation), confirmed absent (authority index + statutes searched, queries recorded, verifier-confirmed), or unknown. Federal conformity is a first-class pack because US states build on federal rails; industry overlays (oil & gas, telecom first) add specialist questions without forking the pipeline.

Source policy (hard constraint). Eligible = public-facing government primaries. Vendor content (Avalara/Vertex/TaxJar class, however free) is noted-only: registered, never fetched into context, never cited, never corroboration. Paywalled or non-government login-gated material is prohibited. Government login-gated data is a needs-human exception — agents hold no credentials. The publish gate mechanically rejects any fact whose citation is not an eligible source.

Implementation Phases

IMPORTANT: Execute every phase and task step by step, in order, top to bottom.

Status markers: [] idle · [wip] in progress · [x] complete · [f] failed. State lives in the plan-manifest island; this page renders it. On handoff, phases become GitHub milestones and task groups become issues — after that, GitHub is status-canonical.

Phase 1: Harness Foundation & Schema Additions

Everything an agent needs to work safely from any harness: the JSON work contract and CLI, AGENTS.md plus adapters (Muse first, goal-based kickoff), model-tier/API-key configuration for Azure AI Foundry, the contextualization layer with its hard scope fence, and the Phase 2 evidence tables with mechanical gates.

Phase 2: Question Packs & Coverage Engine

The interrogation standard as data: category question packs, the peer-profile catalog that makes absence an evidenced finding, the federal conformity pack, and oil-and-gas/telecom industry overlays.

Phase 3: Agent Workflow Units (Conductor, Workers, Verifier, Monitor)

The eight decomposition units implemented as tiered agent work: Wonder conducts and tracks the goal, Glimmer-class workers discover/fetch/extract, an independent verifier re-reads evidence, the human approves last, and the monitor keeps everything current with typed failure feedback.

Phase 4: Federal First Wave & Texas Cascade

Proof at depth: the US Federal profile lands first (states conform to it), Texas state completes all 27 types with history to earliest published data, then counties, cities, transit, and special districts cascade for the sales-tax proof case with combined-rate tie-outs.

Phase 5: World Skeleton & Monitored Refresh

Proof at breadth: every country structure-registered with classified sources (EU as region), a full-world hash refresh with typed exception rollups, and strict virgin-country discipline reserving the demo countries untouched.

Phase 6: Globe, Human Review & Hackathon Demo

The visible surface: a globe rendering live database state, a keyboard-first human review queue (the operator verifies locally, last in the chain), per-jurisdiction evidence packs an auditor can re-perform from, and the rehearsed three-act demo — world refresh, virgin-country population, Texas live maintenance.

Phase 7: Agentic Product Classification (Last Phase)

After rates, rules, licenses, and compliance are populated comes the layer operators feel daily: what is this product, tax-wise, in each place? A coded global product taxonomy (software by delivery mode, short-term-rental lodging, telecom, marketplace-facilitated goods, delivery services…), per-jurisdiction taxability treatments through the same verify-approve chain, and operator product lists in the context profile so niche depth follows what a given client actually sells — maintained and reclassification-monitored like everything else.

Notes

Locked decisions (operator, 2026-11-01)

  • Agent-first, human-last: agents pull, verify, populate, and monitor; downstream custom functions consume the database; the human's only step is final approval. The operator performs verification locally (Texas) for the hackathon build.
  • History to the earliest published data (audit lookback), with earliest-found/searched-earlier evidence.
  • Muse-first, harness-ready: Wonder conducts, Glimmer-class workers extract; Muse/Codex/Grok/OpenCode/Herdr and headless Foundry API runs share the CLI contract. Kickoff is goal-driven on Muse.
  • Contextualization fences every crawl: full-globe is one profile among many (the author's consulting deployment); Texas/Dallas/Brazil examples prove single-footprint operation of the same clone.
  • Sources: public government primaries only; vendor content noted-never-used; no paywalls, no non-government logins, no credentials.
  • Federal first wave, with federal–state conformity links modeled explicitly.
  • Absence is established by peer-profile interrogation plus recorded negative search.
  • Demo: full-world refresh → virgin-country population → populated-country (Texas) live maintenance and approval.
  • Jurisdiction context hooks: per-jurisdiction context packs (local expert guidance and memory) inject pre-run into assignments and hook post-run transitions; guidance never becomes evidence and never relaxes gates.
  • Build visibility: this decree hands off to GitHub milestones + issues; GitHub becomes the status-canonical work queue.

Rejected approaches

  • Persistent per-jurisdiction agents (one process per county/city) — rejected for pooled workers with durable assignments; ~90k US jurisdictions cannot be ~90k processes.
  • Direct SQL by agents — rejected; the CLI is the only write path so gates (eligibility, distinct approvers, context fence) cannot be bypassed by any harness.
  • Vendor data as bootstrap or corroboration — rejected by source policy; a fact without a primary source stays unknown on purpose.
  • Auto-publish on agent confidence — rejected; human approves everything, last. Auto-approval may be revisited only as a future recorded decision with evidence.

Risks

  • Live-demo dependence on third-party government sites: mitigated by backup virgin country, snapshot replay, and rehearsed fallbacks (Phase 6).
  • Token cost of world-scale extraction: mitigated by hash-first monitoring (no LLM for unchanged sources), structure-before-depth ordering, and context fencing for non-global operators.
  • Non-English primaries: language exceptions queue translation with originals preserved; first waves (federal, Texas) are English-published.
